# Model 产品需求计算修改方案

## 目标与交付范围

按产品需求求解具有明确分配关系的多产品 Model。上游参考产出为 100、下游需要 10000 时，通过倍率换算满足需求；同一装置的不同分配产品分别响应各自的下游需求。

实施属于 `platform`，目标分支为 `dev`，工作记录为 [Platform #1196](https://github.com/tiangong-lca/platform/issues/1196)。本文件定义待实现方案，[Model 建模与计算说明](../agents/model-modeling-and-calculation.md)解释目标语义；现有运行行为由[计算代码参考](../agents/util_calculate.md)及源码描述。实现、验证和交付状态在 Issue 与 PR 中维护。

边界：TIDAS schema、SDK 和数据库 schema 保持不变。实现使用现有 Process、LifeCycleModel、过程实例、连接和结果结构。数据库现有保存函数负责同一批次创建过程的版本引用重写；表、列和接口数据结构保持不变。

## 1. 计算问题与修改位置

`compile.ts` 为同一实例的其他产品视图建立 `linkage` 方程，将活动量固定为原始产品产量比；`assemble.ts` 再检查所有已连接输出是否全部被消费。两者共同要求不同产品的需求对应同一个原始过程倍率。

修改后的计算单位是分配后的产品活动。每种产品具有需求方程，活动量由消费者及最终需求共同决定。线性求解、数值残差和产品需求平衡继续负责验证计算结果。

## 2. 数据解释与分配

读取每个节点所引用的精确 Process 版本、参考交换、交换数量、Flow 版本与流类型。以流类型、定量参考和分配目标识别产品，区分产品、基本流及废物流。

| 数据情形                           | 处理                                                 |
| ---------------------------------- | ---------------------------------------------------- |
| 单产品清单或已分配产品清单         | 直接按参考量归一化                                   |
| 多产品清单且适用交换的分配关系明确 | 按产品构造单位清单                                   |
| 多产品清单的必要分配关系不明确     | 返回节点、交换和产品可定位的分配诊断                 |
| 输入参考的处理过程                 | 保持处理服务与输入参考的方向语义，并设置专门回归案例 |

沿用现有标准逐交换分配数组和已有统一份额的解析入口。逐交换声明、未声明交换的参考产品归属、显式零份额和 100% 主功能分配，应形成一张可测试的解释表；数据与方法声明共同确定产品归属。缺失信息与明确的零份额分开表达。

产品 `p` 的参考输出为 `q_p` 时，交换 `e` 的单位量为 `b_e × α_e,p / q_p`。产品参考输出归一为 1，其他联产品参考输出进入各自的产品清单。适用的基本流、边界投入和废物处理义务保留。已分配数量进入派生清单后清除可执行分配项，分配依据保留在方法与来源说明中。

## 3. 需求矩阵与清单汇总

1. 以过程实例和产品交换标识内部产品活动，保留来源节点映射。
2. 按消费活动的单位产品清单形成供应系数 `A`，按参考目标形成 `y`。
3. 求解 `(I − A)x = y`。同一产品的多个消费者累加需求；循环进入同一组方程。
4. 由 `x` 计算每条连接的实际交付量，并汇总各原始画布连接对应的计算连接。
5. 按活动量汇总清单，抵消内部产品交换，保留边界交换；按精确流版本聚合。

分配后的产品活动取消共同原始倍率联动。产品需求残差、有限数检查、负活动量判断、精度和取消机制继续使用统一计算契约。

全局参考产品的最终交付量由 `y` 给出；有循环时总活动量可以大于最终交付量。结果清单的参考数量表达净功能单位。

主结果使用 Model 目标量。单独生成的副产品结果以该产品原始参考数量为默认目标量，明确写入结果参考交换，并使用独立需求向量。该独立结果的活动量与主结果分开保存。主结果中没有需求的支路活动量为零。

## 4. 现有格式中的保存映射

### 分配后过程

为需要展开的产品清单形成标准 Process 数据集。每份数据集具有明确的参考产品、参考量、投入、排放、方法和原始数据来源。单产品过程可以保留原引用及参考量。

派生的单位过程与主、副结果 Process 分别管理：前者是计算图中的供应者，后者是供应链汇总结果。派生过程的类型依据其实际系统边界填写，审核状态来自其自身验证流程。

### 过程实例

每个计算实例引用对应的分配后 Process，保存 `@multiplicationFactor = x / q`。一个画布节点可以映射多个计算实例。标准连接指向实际产品供应者和消费者，并重映射 `referenceToReferenceProcess`。

消费者也展开为多个产品实例时，原始输入连接分别映射到具有正归属需求的消费实例。每个消费实例保持明确供应者，画布边显示这些计算连接的交付量合计。

计算图保留产品实例及有效供应连接，本次功能单位没有需求的实例记录零倍率。独立产品结果通过各自的功能单位组织结果清单。完整编辑图保存在 `json_tg.xflow`，保留原始节点、过程引用及用户连接。

### 标识、版本与生命周期

派生数据标识的作用域包含 Model 身份及版本、原始实例、原始 Process 版本和产品交换。完整清单内容与分配依据决定派生版本；重复保存复用相同身份，模型复制和版本创建遵循各自的版本隔离规则。

以现有 SDK 验证派生 Process 和 LifeCycleModel，以现有保存能力协调模型、派生数据和结果数据。所有新增引用随数据集保存。删除与清理依据所有权和引用关系执行。原始 Process 保持独立。

### 重载与数据包

原生重载从编辑图恢复节点及原始数据版本，重新编译相同产品活动。标准数据包包含计算图、被引用的分配后 Process 和所需依赖。标准导入据此恢复计算图，复算所需信息全部来自包内标准数据及其有效引用。

实现前验证：现有保存接口是否支持所需派生记录及其归属；结果更新/删除是否准确区分两种 Process 角色；导出依赖收集是否覆盖派生引用；标准导入能否构造所需编辑表示。跨仓库接口工作若确有需要，在相应拥有仓库建立任务；schema 与 SDK 约束继续适用。

## 6. 实施顺序

1. 取得反馈模型及其精确依赖版本，记录实际产品角色、分配关系、目标量和两条需求路径。
2. 构造最小分配 Process 与 LifeCycleModel 数据包，验证 SDK、保存、重载、标准导出导入与独立复算，确认保存映射。
3. 实现产品单位清单和需求矩阵，以手算结果验证分配与求解。
4. 实现图映射、派生数据保存、结果管理和重载，并接入诊断及数量展示。
5. 完成数值、数据往返和界面验证，同步计算代码参考与讲解文档，按仓库流程提交评审。

## 7. 验收标准

| 场景 | 可核对结果 |
| --- | --- |
| 参考产量 100，下游需求 10000 | 上游倍率为 100，整份清单同比缩放 |
| 产品产量 100/20，统一分配 80%/20%，原始排放 100；需求 100/10、100/20、100/30 | 排放分别为 90、100、110 |
| 相同案例采用逐交换的不同份额 | 各交换符合自己的分配公式 |
| 旧式 P/Q 份额合计 100%，非参考 R 未声明或显式为 0 | 两种写法等价，R 可独立满足需求且归属负荷为 0 |
| 已保存旧图与主结果，model_version 为显式版本或空值 | 升级保存和新版本保留编辑图、主结果身份、原始引用及历史数据 |
| 所有产品需求等于原始参考产量 | 分配后的适用交换贡献合计重构原始清单 |
| 同一产品供应多个下游 | 供应需求等于各消费者需求之和 |
| 循环 `x = 0.2x + 1` | 活动量 1.25，内部消耗 0.25，最终交付 1 |
| 同一来源 Process 的两个实例 | 实例身份和需求分别计算 |
| 主结果与独立产品结果 | 各自功能单位和上游贡献独立可核对 |
| 已分配结果再次作为供应者 | 等价功能单位下清单一致 |
| 输入参考处理过程及废物处理连接 | 参考量、方向和处理负荷符合手算结果 |
| 保存、重载、修改需求、再次计算 | 来源和产品映射稳定，数量符合新需求 |
| 标准导出、导入、复算 | SDK 验证通过、引用完整、功能单位和结果一致 |
| 缺失/歧义分配、奇异矩阵、非法数值、流版本不匹配 | 诊断定位到相关对象与原因 |
| 微小活动量、取消、并发计算 | 保持有意义的贡献与运行归属 |

采用现有 Jest 数值及保存测试框架，并对改动涉及的编辑、数量显示、诊断与保存重载流程进行渲染验证。执行仓库要求的 lint、build 与提交检查。

## 9. 输入修复与配套启用

缺少分配的非参考产品，以及旧式分配中未声明份额的参考输出，在修复前停止重新计算。已保存结果保留。诊断提供产品、节点和具体处理步骤：补充完整分配或采用已分配过程，明确参考产品份额并确保总份额为 100%，然后引用修复后的过程版本重算。验收覆盖错误原因从 Worker 到服务再到编辑器的传递、失败时不调用保存、节点定位以及修复后的数值结果。

配套验证使用部署了 Database #804 保存函数的非生产环境。先确认目标环境具备同一保存包内新建 Process 引用的版本重写行为，再启用 Platform 产品过程保存能力。在该环境验证编辑器保存与重开，以及标准包导出、导入和重算，核对产品过程的精确版本引用和数值。数据库 Preview 的成功只证明该 Preview，目标部署环境需单独核对。具体环境与执行证据记录在 Issue/PR。
